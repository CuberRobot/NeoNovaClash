# 架构设计

## 1. 一句话概述

项目分为三层：**游戏核心（core） → Web 传输（web） → 前端（frontend）**。
依赖方向只有一条：`web → core`，`frontend → 协议`。
核心层不认识 WebSocket，Web 层不写任何游戏规则，因此规则可以单独测试、对拍与复现。

```text
浏览器 (frontend/js/app.js)
      │  JSON over WebSocket
      ▼
backend/web/websocket.py   连接生命周期、指令分发
      │
backend/web/hub.py         房间注册表、连接映射、后台推进
      │
backend/core/room.py       房间与对局状态机 → 产出待发送消息
      │
backend/core/rules.py      角色池 / 方案校验 / 阵容构建
      │
backend/core/engine.py     战斗引擎（事件化战报）
      │
backend/core/tags.py       标签效果挂载点
backend/core/constants.py  平衡数值（唯一来源）
```

## 2. 各模块职责

| 模块 | 职责 | 不应该做的事 |
| --- | --- | --- |
| `backend/config.py` | 读取环境变量，给出运行参数 | 不读业务规则 |
| `backend/protocol.py` | 定义前后端消息结构、入站校验、下行消息构造 | 不实现游戏逻辑 |
| `backend/web/app.py` | FastAPI 应用、HTTP 路由、静态资源挂载、后台任务启动 | 不直接操作房间状态 |
| `backend/web/hub.py` | 房间号分配与回收、WebSocket 绑定、消息投递、空闲回收 | 不判定胜负 |
| `backend/web/websocket.py` | 连接生命周期、指令分发、把异常翻译成玩家能看懂的提示 | 不写规则 |
| `backend/core/room.py` | 房间与对局状态机、比分、超时、平局重开 | 不知道 WebSocket 存在 |
| `backend/core/rules.py` | 角色池抽取、方案校验、阵容构建、整局模拟入口 | 不生成文案式交互 |
| `backend/core/engine.py` | 战斗主循环与结算顺序 | 不读文件、不连网络 |
| `backend/core/tags.py` | 标签的静态规则与效果钩子 | 不关心谁调用它 |
| `backend/core/constants.py` | 所有平衡数值 | 不写逻辑 |
| `frontend/js/app.js` | 界面状态机、渲染、战报回放 | 不重复实现规则 |

## 3. 一次对局的数据流

```text
玩家点「提交方案」
  → 前端发送 {type: "submit_plan", selection, bonuses, strategy}
  → websocket.py 解析并转成规则层 Plan
  → room.submit(seat, plan)
       ├─ rules.validate_plan：不合法 → RuleError → 前端 error 提示（带 field）
       └─ 合法：记录方案 → 若双方都提交 → room._resolve_round()
            ├─ rules.build_team：角色池 + 方案 + 增益 → Fighter 列表
            ├─ rules.simulate(teams, strategies, seed) → BattleResult（事件列表）
            ├─ 更新比分、写入历史
            └─ 产出 Outgoing 列表：battle_report / round_result / round_start / game_over
  → hub.dispatch：按 seat 投递（None 表示房间内广播）
  → 前端按事件顺序回放，血条与战报实时更新
```

关键点：**房间层只产出「待发送消息」，不直接发送**。
这让房间逻辑可以在没有网络的情况下被完整测试（`tests/test_websocket_flow.py` 之外也可以直接断言 `Outgoing`）。

## 4. 房间状态机

```text
WAITING ──第二人加入──▶ PREPARING ──双方提交/超时──▶ BATTLING
   ▲                        ▲                            │
   │                        └──── 未分出胜负：开下一局 ◀──┤
   │                                                     ▼
   └──────── CLOSED ◀── 掉线/退出 ──────────── FINISHED（三局两胜达成）
```

- `BATTLING` 是瞬态：战斗在一次调用内算完，玩家看不到这个中间态。
- 平局时 `round_index` 不变，重开本局。
- `FINISHED` 后可以「再来一局」：比分清零、历史清空、重新抽池。

## 5. 关键设计决策

**为什么战斗引擎必须可复现？**
每局都用一个明确的种子（`room._round_seed()`），相同输入必然得到同一份战报。
这带来三个好处：玩家复盘不会「对不上」、测试可以直接断言战报文本、平衡性分析可以批量重跑。

**为什么战报是「事件列表」而不是一段长文本？**
事件同时携带结构化数据（`target` / `amount` / `hp_after` / `stacks`…）与一句人话文案。
前端用结构化数据画血条动画，用文案做战报滚动区；将来要做战斗回放分享、数据统计也不需要解析自然语言。

**为什么用整数运算取整？**
`1.4 倍伤害`、`60% 减伤` 这类比例统一用 `value * num // den`，
避免浮点误差导致同一份战报在不同平台上出现 1 点伤害差异。

**为什么把「护盾分担」放在「重装减伤」之前？**
文档的语义是「护盾部署者为队友承担 50% 伤害」，
即先切分伤害，再各自走自己的承伤流程（因此护盾部署者的重装盔甲对自己承担的那一半仍然生效）。

**为什么房间只在内存在线？**
v0.1.0 的目标是把单机双人链路做扎实。房间不落库，进程重启即清空；
代价是水平扩容必须开粘滞会话，这一点已写进部署文档与路线图。

## 6. 扩展指南

### 6.1 新增角色

1. 在 `backend/core/characters.py` 的 `BASE_ROSTER` 追加一条 `Character`；
2. 如果它使用已有标签，到此结束（测试与前端会自动带上）；
3. 补一条测试，并在 `docs/规则设定.md` 的角色表中登记。

### 6.2 新增标签

1. 在 `backend/core/tags.py` 的 `TAGS` 里加 `TagSpec`（文案、次数、限制）；
2. 在 `RUNTIME` 里注册 `TagRuntime`：
   - `modify_outgoing` 改攻击方伤害（参考狂暴）；
   - `modify_incoming` 改受击方承伤（参考重装盔甲）；
   - `on_hit` 做命中后效果（参考中毒、穿透）；
   - `on_damaged` 做受击后效果（参考反弹：按实际损失反打攻击者，且不会再次触发承伤类效果）；
   - `on_battle_start` / `on_round_start` 处理开局与回合开始（参考诅咒、中毒结算）；
   - `targets_all` / `self_destruct_after_attack` 这类开关处理改变出手方式的效果（参考群伤、自爆）；
3. 只有当需要新的结算阶段时才动 `engine.py`，并在 `docs/规则设定.md` 第 3 节补上顺序。

### 6.3 新增模式（混沌 / 大战场）

- 模式差异集中在两处：角色池生成（`rules.generate_pool`）与阵容规模（`constants.TEAM_SIZE` 等）；
- 建议做法：把「模式」抽成 `Mode` 配置对象（池子大小、出战人数、增益次数、是否随机标签），
  `Room` 持有该配置，前端按 `round_start` 下发的参数渲染 —— 现有协议已经把这些参数都发给了前端；
- 切换模式时不要改引擎：引擎只认识「几支队伍、每队几个战士」。

### 6.4 接入新的前端

任何客户端只要实现 `docs/通信协议.md` 里的消息即可。
服务端不区分浏览器、机器人或命令行：`tools/smoke_pvp.py` 就是一个只有 100 多行的纯机器人客户端。

## 7. 测试策略

| 测试文件 | 覆盖内容 |
| --- | --- |
| `tests/test_engine.py` | 9 种标签效果的边界（阈值上下、上限、次序）、可复现性、回合上限、完整战报结构 |
| `tests/test_rules.py` | 角色池、方案校验的每一条错误分支、增益上限、阵容构建、随机方案合法性 |
| `tests/test_api.py` | HTTP 接口与规则数据的一致性 |
| `tests/test_websocket_flow.py` | 建房 → 加入 → 提交 → 结算 → 三局两胜、私有信息不泄露、非法提交报错、断线关房、超时自动提交 |
| `tools/balance.py` | 平衡对拍：角色抽到率 / 出战率 / 出战胜率、标签胜率、先手优势（调数值前先跑它） |

约定：**修 bug 先补一条会失败的测试**，再改实现。

## 8. 已知限制

- 刷新页面或断线即退出房间（不做重连），对手会收到「房间已关闭」提示；
- 房间状态在内存中，多进程/多实例需要粘滞会话或 Redis；
- 没有账号体系、排行榜与观战；
- 前端为原生 JS，没有构建步骤（换来的是部署零依赖，代价是复杂交互要靠约定维护）。

这些都记录在 [开发路线图](开发路线图.md) 中，按优先级逐步处理。
