### 1.2 由此得出的三个判断

1. **稳定性已经达标**：连续 6.3 天无重启、无异常，`/api/health` 一直正常 —— v1.0 的第 1 条门槛（线上稳定一周）基本满足。
2. **瓶颈不是"玩法不够"，而是"来了之后没有第二局"**：20 个 IP、7 场战斗，说明大部分人点进来看了看就走了。现在再加玩法，只会让第一次来的人更迷茫。
3. **数值平衡暂时不能靠真人数据**：7 场战斗连一个角色的胜率都算不出来。想调平衡只能继续用 `tools/balance.py` 的对拍，或者先把人留住。

### 1.3 一个必须承认的运维缺口

服务器**没有落盘日志**：systemd 没配 `StandardOutput`，`journalctl` 里查不到任何东西（`No journal files were found`）。
现在排查问题只能靠 nginx 的访问日志 + `/api/health`。
上次"为什么总能匹配到"这个问题，就是因为没有日志，我只能靠间接证据推断。

> **2026-09-25 已修复**：见 §3.1 的完成标记与 [运维手册](运维手册.md)。
> 现在 `/www/wwwlogs/neonovaclash.app.log` 里有结构化的 `room_created` / `battle_start` /
> `match_over` / `room_closed`，一行 grep 就能回答"昨天多少人开房、打完几局"。

## 3. 怎么做（按优先级，附验收标准）

### 3.1 先补运维与可观测（不抬版本号）

理由：没有日志就没法判断"人是被哪一步劝退的"，后面所有优化都会变成盲猜。

| 任务 | 做法 | 验收标准 |
| --- | --- | --- |
| 应用日志落盘 ✅ 2026-09-25 | systemd 加 `StandardOutput=append:/www/wwwlogs/neonovaclash.app.log`（或开 journald 持久化），并按天轮转 | 重启后能看到启动日志、异常堆栈、房间生命周期 → **已验证** |
| 关键事件打点 ✅ 2026-09-25 | 房间创建/关闭、匹配命中、对局结束各打一行结构化日志（房间号、模式、局数、胜负、是否超时） | `grep` 一行就能回答"昨天有多少人开房、打完几局" → **已验证**（见 [运维手册](运维手册.md) §3.2） |
| 错误上报 | 前端未捕获异常带上时间戳与版本号；后端异常带 request id | 线上出问题能定位到具体版本与时间 |
| 备份与回滚演练 | 记录一次真实的 `git checkout <tag> && deploy/update.sh` 演练结果 | 文档里写下演练时间与结果，回滚 < 2 分钟 |

> 2026-09-25 追加（原计划外，但属于同一类"让问题看得见"）：**SSH 改密钥登录 + 关闭密码认证 + fail2ban**。
> 起因是这轮审计发现服务器每天被爆破上万次、root 密码登录且无公钥。详见 [运维手册](运维手册.md) §2。

### 3.2 新手路径（第一个真正的 +0.1 版本，v0.13.0）

理由：20 个 IP 只换来 7 场战斗，问题在"进得来、玩不下去"。

| 任务 | 现状 → 目标 | 验收标准 |
| --- | --- | --- |
| 首屏直接给"马上开打" | 现在要点「练习模式」才知道能一个人玩 → **首屏放一个最显眼的「先跟电脑打一局」**，真人匹配和创建房间并列 | 新访客 3 次点击内进入备战 |
| 第一次进备战的引导 | 无 → 一屏半透明提示：拖牌 → 放增益 → 提交（可关闭，不再出现） | 清空 localStorage 后能看到，点过就记住 |
| 对局结束的下一步 | 结算页只有"再来一局 / 返回大厅" → 增加"换一种模式再打"与战绩摘要 | 结算页能一键进入下一种模式 |
| 分享更容易 | 邀请链接已存在 → 结算页增加"把刚才这局分享出去"（含双方阵容与比分的只读链接） | 链接打开能看到战报，不需要登录 |
| 战绩本地化文案 | 现在只有 5 条记录 → 改成"胜率 + 最近 5 场 + 最高连胜" | 大厅一眼能看到进步 |

> 为什么把"分享战绩"放进来：你首发是靠发链接，**让玩家能把自己的战绩发出去**比再多一个模式更能带来新玩家。

> **2026-09-25 补充**：这一节是"提升第一局完成率"的产品工作，**不改变玩法上限**。
> 如果目标是让会玩的人愿意反复玩，需要的是机制层面的改动——
> 决策空间量化、三条路线与取舍见 **[玩法评估与下一步](玩法评估与下一步.md)**。
> 两件事不要混：先做本节（低风险、可验证），机制手术按那份文档拍板后再动。

### 3.3 玩法深度（v0.14.0 之后，二选一或都做）

| 方向 | 内容 | 前置条件 |
| --- | --- | --- |
| 观战模式 | 房间支持观众（上限 4），只收战报不参与提交；提交前不泄露任何私有信息 | 需要有人同时在玩，否则没人观战 |
| 电脑对手升级 | 现在的电脑是"随机合法阵容"；升级为①会按你上一局阵容挑克制标签，②第三局反过来针对你的习惯 | 需要记录玩家上一局阵容（本地即可） |
| 大战场差异化 | 给对拍工具加 `--mode`，跑一轮大战场专属平衡（团队标签在 5v5 权重更高） | 先补工具，再动数值 |
| 补卡调参 | 候选数 3→4、或"换牌"而非"加牌" | 先用对拍看数据，再让真人试 |

### 3.4 工程债（穿插做，不单独发版）

- **交互回归脚本**：两种视图 × 三种模式 × 3/5 人阵容，用 Playwright 跑一遍（目前靠人工点）；
- **大战场/混沌模式的测试补齐**：现在模式差异主要靠配置，缺少"模式间不串味"的端到端用例扩充；
- **移动端**：5v5 战场在手机上的布局与拖拽手感复验；
- **`/api/health` 继续加**：在线人数趋势、平均对局时长（用于判断留存）。

## 4. 明确"不做"（防止再次膨胀）

| 不做 | 原因 | 什么时候再考虑 |
| --- | --- | --- |
| 账号系统 / 登录 | 现在连留存都没有，账号只会增加门槛 | 有稳定回访玩家之后 |
| 段位 / 排位 | 同时在线人数不足两位数，匹配分层会把等待时间拉到不可接受 | 同时在线 ≥ 50 |
| Redis / 多实例横向扩容 | 单进程内存房间完全够用（6 天 5 个房间） | 同时在线 ≥ 200 或需要滚动发布 |
| 新增第 4 个模式 | 三个模式的差异化还没被玩透 | 现有模式的留存数据说话之后 |
| 大规模 UI 改造 | 卡牌模式刚上线，先收集真实反馈 | — |

## 5. 建议的执行顺序

```text
第 1 步（本周）  日志落盘 + 关键事件打点 + 回滚演练        ← ✅ 日志与打点已完成（2026-09-25）
                                                              顺带补了 SSH 密钥化 + fail2ban
第 2 步（本周）  新手路径 5 项                            ← v0.13.0（玩家能感知，+0.1）
第 3 步（下周）  观察一周数据：开局率 / 完成率 / 回访率     ← 用数据决定第 4 步做什么（现在终于有数据了）
第 4 步          观战 或 电脑对手升级（二选一）             ← v0.14.0
第 5 步          大战场平衡 + 补卡调参（对拍驱动）          ← v0.14.x
第 6 步          四条门槛全绿 → 打 v1.0.0                  ← 对外正式版
```

每个步骤都遵守：**先写验收标准 → 做 → 用浏览器/线上实测 → 文档同步 → 该抬号才抬号。**
