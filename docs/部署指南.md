# 部署指南

## 1. 环境要求

- Python **3.10+**（开发机使用 3.14 验证；3.10 是语法下限）
- 无需数据库、无需 Node 构建（前端是原生静态文件）
- 对外只暴露一个 HTTP 端口，WebSocket 走同一端口同一个路径 `/ws`

## 2. 本地 / 单机部署（venv）

```bash
git clone <仓库地址> && cd NeoNovaClash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt

python run.py                       # 读取环境变量，默认 0.0.0.0:8000
```

验证：

```bash
curl -s http://127.0.0.1:8000/api/health      # => {"status":"ok",...}
curl -s http://127.0.0.1:8000/api/version
```

## 3. 生产进程（uvicorn / systemd）

```bash
./venv/bin/uvicorn backend.web.app:app --host 0.0.0.0 --port 8000 --workers 1
```

> **注意**：房间状态保存在进程内存里，`--workers` 大于 1 时必须开启粘滞会话，
> 否则同一名玩家两次连接可能落到不同进程。单进程足以支撑内部对局与朋友间的对战。

systemd 单元示例（`/etc/systemd/system/neonovaclash.service`）：

```ini
[Unit]
Description=NeoNovaClash
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/opt/NeoNovaClash
Environment=NC_HOST=127.0.0.1
Environment=NC_PORT=8000
Environment=NC_PREPARE_TIMEOUT=60
ExecStart=/opt/NeoNovaClash/venv/bin/uvicorn backend.web.app:app
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now neonovaclash
journalctl -u neonovaclash -f
```

## 4. Docker

```bash
docker compose up --build -d      # 构建并后台启动，映射 8000 端口
docker compose logs -f
docker compose down
```

或者只用 Docker：

```bash
docker build -t neonovaclash:latest .
docker run -d --name neonovaclash -p 8000:8000 \
  -e NC_PREPARE_TIMEOUT=60 -e NC_MAX_ROOMS=500 neonovaclash:latest
```

镜像里已经带了 `HEALTHCHECK`，探针指向 `/api/health`。

## 5. 反向代理（nginx）

WebSocket 需要显式转发升级头，否则前端会卡在「连接中…」：

```nginx
server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket 升级
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 300s;   # 比空闲心跳间隔长即可
    }
}
```

启用 HTTPS 后前端会自动使用 `wss://`（代码里按 `location.protocol` 判断），不需要改配置。

## 6. 环境变量

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `NC_HOST` | `0.0.0.0` | 监听地址，放在 nginx 后面建议改成 `127.0.0.1` |
| `NC_PORT` | `8000` | 监听端口 |
| `NC_PREPARE_TIMEOUT` | `60` | 备战限时（秒） |
| `NC_ROOM_TTL` | `1800` | 等待中/已结束房间的空闲回收时间（秒） |
| `NC_MAX_ROOMS` | `500` | 单进程最大房间数，防止内存被占满 |
| `NC_LOG_LEVEL` | `info` | 日志级别：critical / error / warning / info / debug |

## 7. 运行时行为说明

- **后台任务**：服务每 1 秒推进一次房间（处理备战超时、回收空闲房间）；
- **房间生命周期**：任意一方掉线或主动退出，房间立即关闭，对手会收到明确提示；
- **无持久化**：进程重启后所有房间清空，这是 v0.1.0 的已知取舍；
- **资源占用**：一场对局的战报约几十 KB 内存，`NC_MAX_ROOMS=500` 时占用可以忽略。

## 8. 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 页面一直显示「连接中…」 | 反向代理没有转发 WebSocket 升级头，按第 5 节补上 `Upgrade` / `Connection` |
| 加入房间提示「房间不存在或已关闭」 | 房间号输错，或对手已经离开/房间被回收 |
| 刚进对战就被自动提交 | 备战超时（默认 60 秒），可调大 `NC_PREPARE_TIMEOUT` |
| 两人看不到对方 | 确认双方访问的是同一个地址；跨网络部署时房间号对应的是同一个服务实例 |
| `address already in use` | 端口被占用，改 `NC_PORT` 或结束占用进程 |
| 战斗中刷新页面 | 当前版本视为掉线，房间会关闭，重新建房即可（重连在路线图中） |
