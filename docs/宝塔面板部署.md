# 宝塔面板部署（含 WebSocket 反代）

本文记录的是「用一台装了宝塔面板的 Linux 服务器，把 NeoNovaClash 跑成可对外访问的 demo」
这套做法，也是本项目线上 demo 当前使用的方案。**文中不包含任何服务器密码或面板凭据**，
凭据请只保存在你自己的密码管理器里。

## 0. 部署结构

```text
浏览器
  │  http://<服务器IP>/            （WebSocket 走同一端口的 /ws）
  ▼
宝塔自带的 nginx :80
  │  反向代理（带 WebSocket 升级头）
  ▼
127.0.0.1:8010   ← systemd 服务 neonovaclash（www 用户）
  │
/www/wwwroot/neonovaclash   ← 代码 + venv
```

要点：应用只监听回环地址，对外只暴露 80（或你申请的域名 + 443），
这样既不用额外开放端口，也能让宝塔面板统一管理证书与访问日志。

## 1. 前置检查

```bash
cat /etc/os-release | head -2      # 本文以 Debian 12 为例
python3 -V                         # 需要 3.10+，推荐 3.11/3.12
nginx -v                           # 宝塔自带 nginx 即可
ls /www/server/panel              # 确认宝塔面板存在
```

如果 `python3 -m venv` 报 `No module named 'ensurepip'`，先补依赖：

```bash
export DEBIAN_FRONTEND=noninteractive
apt-get update -qq
apt-get install -y python3-venv python3-pip
```

## 2. 拉代码并创建虚拟环境

```bash
mkdir -p /www/wwwroot
git clone https://github.com/CuberRobot/NeoNovaClash.git /www/wwwroot/neonovaclash
cd /www/wwwroot/neonovaclash

python3 -m venv venv
venv/bin/pip install --upgrade pip
venv/bin/pip install -r requirements.txt
```

自检（可选，建议第一次部署都跑一遍）：

```bash
venv/bin/python -m pytest -q          # 需要先 pip install -r requirements-dev.txt
```

## 3. 注册 systemd 服务

仓库里已经准备好了服务模板 [deploy/neonovaclash.service](../deploy/neonovaclash.service)：

```bash
cp /www/wwwroot/neonovaclash/deploy/neonovaclash.service /etc/systemd/system/neonovaclash.service
chown -R www:www /www/wwwroot/neonovaclash
systemctl daemon-reload
systemctl enable --now neonovaclash
systemctl status neonovaclash --no-pager
```

两个容易踩的坑：

1. **必须用 `python run.py` 启动**，不要写成 `uvicorn backend.web.app:app`。
   uvicorn 命令行不会读取 `NC_HOST` / `NC_PORT` 环境变量，会默认监听 127.0.0.1:8000，
   于是 nginx 反代到 8010 就会连不上。
2. **不要加 `--workers`**。房间状态存在进程内存里，多进程会让同一名玩家的两次连接落到不同进程。

验证：

```bash
ss -lntp | grep 8010                          # 应该看到 127.0.0.1:8010
curl -fsS http://127.0.0.1:8010/api/health    # {"status":"ok",...}
```

## 4. 配置 nginx 反向代理

仓库里的模板：[deploy/nginx.neonovaclash.conf](../deploy/nginx.neonovaclash.conf)

```bash
cp /www/wwwroot/neonovaclash/deploy/nginx.neonovaclash.conf \
   /www/server/panel/vhost/nginx/neonovaclash.conf

nginx -t && nginx -s reload
```

模板里最关键的是这几行，**缺了 WebSocket 头，前端会一直停在「连接中…」**：

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
proxy_read_timeout 300s;
```

### 想用宝塔面板界面来做也行

1. 面板 → **网站** → 添加站点（域名填服务器 IP 或你的域名，不要选 PHP）；
2. 进入该站点 → **反向代理** → 添加反向代理：
   - 代理名称：`neonovaclash`
   - 目标 URL：`http://127.0.0.1:8010`
   - 发送域名：`$host`
   - **务必勾选「开启 WebSocket 支持」**；
3. 需要 HTTPS 时，在同一站点里申请 Let's Encrypt 证书即可，
   前端会自动使用 `wss://`（代码按 `location.protocol` 判断），不用改任何配置。

## 5. 验收

```bash
# 服务器本机
curl -fsS -H "Host: <服务器IP>" http://127.0.0.1/api/version

# 从你自己的电脑
curl -fsS http://<服务器IP>/api/health

# 用两个机器人客户端在线上跑完整场三局两胜（本仓库自带）
python -m tools.smoke_pvp --url ws://<服务器IP>/ws

# 最真实的一步：用两个浏览器标签页各开一局，确认：
#   大厅 → 创建/加入房间 → 选人布阵 → 战报回放 → 比分结算 → 再来一局
```

如果外网打不开但服务器本机 `curl` 正常，问题通常在**云厂商的安全组**里没有放行 80/443。

## 6. 更新与回滚

仓库提供了一键更新脚本 [deploy/update.sh](../deploy/update.sh)：

```bash
bash /www/wwwroot/neonovaclash/deploy/update.sh
# 等价于：git pull --ff-only && pip install -r requirements.txt && systemctl restart neonovaclash && 健康检查
```

脚本会先执行 `git config --global --add safe.directory "$APP_DIR"`：
用 root 操作 `www` 用户拥有的目录时，git 默认会以「dubious ownership」拒绝执行。

回滚到某个稳定版本（tag）：

```bash
cd /www/wwwroot/neonovaclash
git fetch --tags
git checkout v0.1.0
bash deploy/update.sh
```

## 7. 宝塔面板里还能做什么

| 需求 | 在面板里的位置 |
| --- | --- |
| 看服务是否在跑、重启 | 终端里 `systemctl status/restart neonovaclash`（面板不显示自定义 systemd 服务） |
| 看访问日志 | 面板 → 网站 → 站点 → 日志；或 `/www/wwwlogs/neonovaclash.log` |
| 配置域名与 HTTPS | 网站 → 站点 → 域名管理 / SSL |
| 控制端口开放 | 面板 → 安全（同时别忘了云厂商控制台的安全组） |
| 升级 Python 依赖 | 终端执行 `deploy/update.sh` |

## 8. 安全注意事项

- **面板凭据不要进仓库**：本文档与仓库里没有任何密码；也请勿把服务器密码写进
  `.env`、README 或提交信息。建议面板开启「面板 SSL + 二次验证 + IP 白名单」，
  并避免把面板端口暴露在公网。
- **demo 目前没有登录鉴权**：任何知道地址的人都能创建房间（房间里只有对局数据）。
  如果要长期公开，建议加一层 nginx Basic Auth 或在应用里加房间密码。
- **443 未开放时不要用 https 访问**：会一直连接超时；要么在云安全组放行 443 并用面板申请证书，
  要么就用 http。
- **房间是内存态**：重启服务会清空所有房间，玩家需要重新建房（重连功能在路线图里）。
- 建议给 demo 设一个较低的 `NC_MAX_ROOMS`（模板里是 200），防止被刷房间占满内存。

## 9. 常见问题

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 页面停在「连接中…」 | nginx 缺 WebSocket 升级头 | 按第 4 节补 `Upgrade` / `Connection` |
| 502 Bad Gateway | 应用没在 8010 监听 | 用 `python run.py` 启动；`ss -lntp \| grep 8010` 确认 |
| 外网完全打不开 | 云厂商安全组没放行 | 安全组放行 80（以及 443） |
| 加入房间提示「房间不存在」 | 房间号错误、对手已离开、或服务重启过 | 重新建房 |
| 刚进对战就被自动提交 | 备战超时（默认 90 秒） | 调大 `NC_PREPARE_TIMEOUT` 后重启服务 |
| 两人互相看不到对方 | 两人连的不是同一个实例 | 确认访问同一个地址 |

## 11. 接入 Cloudflare CDN

Cloudflare 不能代理裸 IP，所以需要先把域名（本项目的 demo 域名是 `novaclash.cc`）添加到 Cloudflare。

### 11.1 Cloudflare 后台设置

| 项目 | 位置 | 取值 |
| --- | --- | --- |
| DNS 记录 | DNS → Records | `A` `@` → 服务器 IP，代理状态**橙云（Proxied）** |
| SSL 模式 | SSL/TLS → Overview | 源站已开 443 时用 **Full (strict)**；源站只有 80 时临时用 **Flexible** |
| 强制 HTTPS | SSL/TLS → Edge Certificates | Always Use HTTPS：开；Automatic HTTPS Rewrites：开 |
| 最低 TLS | 同上 | TLS 1.2 |
| 缓存规则 | Rules → Cache Rules | `/ws*` 与 `/api/*` → **Bypass cache**（否则 WebSocket 握手与实时数据会被缓存破坏） |
| Rocket Loader | Speed → Optimization | **必须关**，它会打乱前端 JS 的加载顺序 |
| Bot Fight Mode | Security → Bots | 建议**关**，否则可能拦截 WebSocket 握手与压测机器人 |

### 11.2 源站要配合的两件事

1. **把域名写进 `server_name`**（已包含在 `deploy/nginx.neonovaclash.conf`）：
   `server_name novaclash.cc www.novaclash.cc <服务器IP>;`
2. **回源真实 IP**：把 `deploy/nginx.cloudflare-realip.inc` 装到
   `/www/server/panel/vhost/nginx/neonovaclash-cf-realip.inc`，
   两个 server 块里已经 `include` 了它（文件名用 `.inc`，避免被宝塔的 `*.conf` 通配吞掉）。

```bash
cp deploy/nginx.cloudflare-realip.inc /www/server/panel/vhost/nginx/neonovaclash-cf-realip.inc
cp deploy/nginx.neonovaclash.conf     /www/server/panel/vhost/nginx/neonovaclash.conf
nginx -t && nginx -s reload
```

### 11.3 开启 443（Full (strict) 的前提）

源站本机 ufw 默认已放行 443，**真正会挡住的是云厂商控制台的安全组**。
在安全组放行 443 后，用 Cloudflare 的源站证书建 443 站点：

```bash
# 1. Cloudflare 后台 → SSL/TLS → Origin Server → Create Certificate
#    主机名填 novaclash.cc, *.novaclash.cc，有效期选 15 年，得到证书与私钥
# 2. 保存到宝塔的证书目录
mkdir -p /www/server/panel/vhost/cert/neonovaclash
#    把证书内容写入 fullchain.pem、私钥写入 privkey.pem
# 3. 装 443 站点并重载
cp /www/wwwroot/neonovaclash/deploy/nginx.neonovaclash-ssl.conf \
   /www/server/panel/vhost/nginx/neonovaclash-ssl.conf
nginx -t && nginx -s reload
# 4. 回到 Cloudflare：SSL/TLS → Overview → Full (strict)
```

> 源站证书只在 Cloudflare 代理下受信（浏览器直连会提示不受信），这是预期行为。
> 想直连也受信，就在宝塔里用 Let's Encrypt 给站点签一张证书。

### 11.4 排错：522 / 521 / 520

| 现象 | 含义 | 处理 |
| --- | --- | --- |
| **522** | Cloudflare 连不上源站（TCP 层） | 最常见是 SSL 模式为 Full/Full (strict) 但源站 443 被安全组挡住 → 放行 443，或临时切 Flexible |
| 521 | 源站拒绝连接（Web 服务没在监听） | `systemctl status neonovaclash`、`ss -lntp \| grep 8010` |
| 520 | 源站返回了 Cloudflare 无法解析的响应 | 看 `/www/wwwlogs/neonovaclash.error.log` |
| 访问域名返回宝塔默认页 | 请求落到了别的 server 块 | 确认 `server_name` 里包含该域名；`curl -H "Host: 域名" http://127.0.0.1/` 自测 |
| HTTPS 能开但 WebSocket 连不上 | nginx 缺 `Upgrade`/`Connection` 头，或缓存规则没放行 `/ws` | 见 11.1 与第 4 节 |

### 11.5 Cloudflare 免费版的 WebSocket 限制

空闲连接 **100 秒**会被 Cloudflare 断开。本项目前端每 25 秒发送一次 `ping`，
正好在这个限制内，所以无需额外配置；如果你换了自己的前端，记得保留心跳。

### 11.6 让 www 自动跳到主域名

推荐两层一起做，任何一层失效都还能跳：

**① 源站（已经配置在 `deploy/nginx.neonovaclash.conf` 与 `-ssl.conf` 里）**

nginx 为 `www.novaclash.cc` 单独开了一个 server 块，直接返回 301 到主域名，
并且保留路径和查询参数（`$request_uri`）：

```nginx
server {
    listen 80;
    server_name www.novaclash.cc;
    return 301 https://novaclash.cc$request_uri;
}
```

注意：跳转的目标 host 从 `www` 变成了主域名，所以不会和 Cloudflare 的
Always Use HTTPS 形成死循环；反过来，主域名那一块绝对不能写 301 跳 https。

**② Cloudflare 边缘（推荐，省一次回源）**

1. DNS → Records → 新增：类型 `CNAME`、名称 `www`、内容 `novaclash.cc`、**橙云**；
   （也可以再建一条 A 记录指向服务器 IP，效果相同）
2. Rules → **Redirect Rules** → Create rule：
   - When incoming requests match：`Hostname equals www.novaclash.cc`
   - Then：`Dynamic` → 表达式 `concat("https://novaclash.cc", http.request.uri.path)`
   - Status code：`301`，勾选 **Preserve query string**；
3. 老界面里也可以用 Page Rules：`www.novaclash.cc/*` → Forwarding URL (301)
   → `https://novaclash.cc/$1`。

做完之后访问 `http://www.novaclash.cc/规则` 应该跳到 `https://novaclash.cc/规则`。

### 11.7 Cloudflare Tunnel（机房拦截 CF 回源时的正解）

如果 DNS 已经指向源站、灰云能访问、橙云却一直 522，而且源站访问日志里**看不到任何来自
Cloudflare 的请求**，说明机房在回源路径上拦掉了 Cloudflare。这时不要继续折腾 SSL 模式与端口，
改用 **Cloudflare Tunnel**：由服务器**主动出站**连接 Cloudflare，不需要任何入站端口，
也就完全不受安全组与机房策略影响，同时自带 HTTPS 与 WebSocket。

本项目线上 demo 就是这么解决的，完整步骤如下。

```bash
# 1) 安装 cloudflared
cd /tmp
curl -fsSL -o cloudflared.deb \
  https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64.deb
dpkg -i cloudflared.deb

# 2) 登录授权（会打印一个 dash.cloudflare.com 链接，在浏览器里选域名并 Authorize）
cloudflared tunnel login

# 3) 创建命名隧道
cloudflared tunnel create novaclash
ls /root/.cloudflared/            # 得到 <隧道ID>.json（密钥）与 cert.pem

# 4) 写配置（把隧道 ID 换成上一步输出的）
mkdir -p /etc/cloudflared
cp /www/wwwroot/neonovaclash/deploy/cloudflared-config.yml /etc/cloudflared/config.yml
chmod 600 /etc/cloudflared/config.yml
#    模板见 deploy/cloudflared-config.yml：ingress 指向 http://127.0.0.1:80，
#    交给 nginx 处理 Host 路由与 www 跳转

# 5) 把域名解析指向隧道（会覆盖原有 A 记录，代理状态保持橙云）
cloudflared tunnel route dns -f novaclash novaclash.cc
cloudflared tunnel route dns -f novaclash www.novaclash.cc

# 6) 装成系统服务
cloudflared service install
systemctl enable --now cloudflared
systemctl status cloudflared --no-pager
```

配套的源站设置：

- `deploy/nginx.cloudflare-realip.inc` 里额外加了 `set_real_ip_from 127.0.0.1;` 与 `::1;`，
  否则走隧道时 nginx 只会看到本机地址，日志里拿不到访客真实 IP；
- 走隧道后**可以关掉云安全组里的 80/443**，源站不再需要任何入站 Web 端口，攻击面更小；
- SSL/TLS 模式在隧道下不再影响回源（cloudflared 直接连本地服务），保持 Flexible 或 Full 都可以。

临时验证用的快速隧道（不需要域名与授权，地址随机、重启即失效）：

```bash
systemd-run --unit=nc-quicktunnel --collect \
  --property=StandardOutput=file:/tmp/quicktunnel.log \
  --property=StandardError=file:/tmp/quicktunnel.log \
  /usr/bin/cloudflared tunnel --url http://127.0.0.1:8010 --no-autoupdate
grep -oE "https://[a-z0-9.-]+\.trycloudflare\.com" /tmp/quicktunnel.log | head -1
```
