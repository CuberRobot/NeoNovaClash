# 通信协议

> 协议版本：`1`（`GET /api/version` 返回的 `protocol` 字段）
> 传输：浏览器与服务器通过 `GET /ws` 建立 WebSocket，消息体统一为 JSON 文本。

## 1. 连接与握手

连接成功后服务端立即推送一条 `hello`：

```json
{ "type": "hello", "server": "NeoNovaClash", "version": "0.1.0", "protocol": 1, "message": "已连接到星核竞技场" }
```

客户端可以随时发送 `{"type":"ping"}`，服务端回复 `{"type":"pong"}`（前端每 25 秒发一次，用于保活）。

## 2. 客户端 → 服务端

| `type` | 字段 | 说明 |
| --- | --- | --- |
| `create_room` | `name`, `mode` | 创建房间；`mode` 取 `standard` / `chaos` / `big_battlefield`，缺省为标准模式 |
| `join_room` | `name`, `room_code` | 用房间号加入，占座为 B 队（seat 1），人满即自动开局 |
| `join_random` | `name`, `mode` | **随机匹配**：只在**相同模式**的队列里配对 |
| `create_practice` | `name`, `mode` | **练习模式**：开一个带电脑对手的房间，不进匹配队列 |
| `cancel_matchmaking` | — | 取消随机匹配排队 |
| `reconnect` | `room_code`, `token` | **断线重连**：用加入时拿到的 token 回到原来的座位 |
| `submit_plan` | `selection[]`, `bonuses[]`, `strategy` | 提交或更新本局方案，双方都提交后立即结算 |
| `replay_done` | — | 客户端确认上一局的回放已经播完（或玩家点了「跳到结果」）；**两边都确认后本局倒计时才开始** |
| `pick_card` | `char_id` | **补卡**：把候选里的一张收进本场角色池（第二局起每局一次） |
| `rematch` | — | 对局结束后请求再来一局（双方都请求才生效） |
| `leave_room` | — | 主动离开房间（房间立即关闭） |
| `ping` | — | 心跳 |

### 2.1 `submit_plan` 结构

```json
{
  "type": "submit_plan",
  "selection": [1, 9, 7],
  "bonuses": [
    { "slot": 1, "kind": "atk" },
    { "slot": 1, "kind": "hp" },
    { "slot": 2, "kind": "atk" },
    { "slot": 3, "kind": "hp" }
  ],
  "strategy": { "kind": "lowest_hp", "tag": null }
}
```

- `selection`：角色编号数组，顺序即出击顺序，必须恰好 3 个且都在本局角色池中；
- `bonuses`：`slot` 为出击位（1 起），`kind` 取 `atk`（+2）或 `hp`（+4），必须恰好 4 次，单个 `slot` 最多 2 次；
- `strategy.kind`：`lowest_hp` / `highest_atk` / `tag_priority`；
  当取 `tag_priority` 时必须提供 `tag`（例如 `"berserk"`）。

## 3. 服务端 → 客户端

| `type` | 关键字段 | 说明 |
| --- | --- | --- |
| `hello` | `version`, `protocol` | 连接建立 |
| `room_joined` | `room_code`, `seat`, `token`, `score`, `players[]`, `phase` | 房间信息（含自己的座位与重连 token） |
| `opponent_joined` | `name` | 对手进入房间 |
| `matchmaking_waiting` | `queue_size` | 已进入随机匹配队列 |
| `matchmaking_cancelled` | — | 已退出随机匹配队列 |
| `opponent_disconnected` | `name`, `grace_seconds` | 对手掉线，房间保留 `grace_seconds` 秒等待重连 |
| `opponent_reconnected` | `name` | 对手已重连回来 |
| `state_sync` | `phase`, `pool[]`, `plan`, `submitted`, `opponent_ready`, `remaining_seconds`, `awaiting_replay`, `final` … | 重连成功后的一次性状态同步；`phase="finished"` 时带 `final`（整场结果），客户端据此重新弹出结算页而不是回大厅 |
| `round_start` | `round_index`, `pool[]`, `candidates[]`, `draft_size`, `deadline_seconds`, `awaiting_replay`, `players[]`, `score`, `strategies[]`, `team_size`, `mode`, `random_tags` … | 新一局开始，**`pool` 只包含自己的角色池**（整场底牌相同，补过的牌会累积在里面）；`candidates` 是补卡候选（第一局为空）；`players[]` 带双方昵称与 `is_bot`（前端显示"对手：xxx"）；`awaiting_replay=true` 表示倒计时还没开始，等客户端发 `replay_done` |
| `prepare_started` | `round_index`, `deadline_seconds` | 双方都看完回放（或 30 秒兜底到点），本局倒计时正式开始 |
| `pool_updated` | `round_index`, `pool[]`, `card`, `auto` | 补卡生效后的新角色池；`auto=true` 表示玩家没选、系统随机补的 |
| `plan_accepted` | `plan` | 方案通过校验 |
| `plan_auto_submitted` | `plan`, `reason` | 超时后系统代提交的方案 |
| `opponent_ready` | — | 对手已提交（不泄露对手内容） |
| `battle_report` | `round_index`, `lineups[]`, `plans[]`, `result`, `score`, `auto_submitted[]` | 本局战报：开战阵容、双方方案、完整事件列表 |
| `round_result` | `winner_seat`, `score`, `match_over`, `reason`, `rounds` | 本局结果与最新比分 |
| `game_over` | `winner_seat`, `score`, `history[]`, `players[]` | 整场结束 |
| `opponent_rematch` | — | 对手请求再来一局 |
| `rematch_started` | — | 双方都同意，重新开局 |
| `room_closed` | `reason` | 房间关闭（对手离开/超时回收） |
| `left_room` | — | 自己已离开房间 |
| `error` | `message`, `field`, `fatal` | 出错提示；`fatal=true` 表示当前房间上下文已失效 |
| `pong` | — | 心跳回复 |

### 3.1 `round_start`（私有信息）

> 说明：`room_joined` 与 `state_sync` 的私有信息约定见 3.1.1 / 3.1.2。

```json
{
  "type": "round_start",
  "room_code": "N7BP",
  "round_index": 1,
  "score": [0, 0],
  "deadline_seconds": 60,
  "pool": [
    { "id": 9, "name": "风行射手", "role": "输出", "atk": 7, "hp": 21, "initiative": 4,
      "tag": "pierce", "tag_name": "箭矢穿透", "tag_summary": "…", "domain": "迅流星域",
      "lore": "…", "place_first": false }
  ],
  "strategies": [
    { "kind": "lowest_hp", "label": "优先攻击当前血量最低的敌人", "need_tag": false }
  ],
  "team_size": 3,
  "pool_size": 6,
  "bonus_per_round": 4,
  "bonus_options": [{ "kind": "atk", "label": "攻击 +2" }, { "kind": "hp", "label": "生命 +4" }],
  "max_bonus_per_fighter": 2,
  "rounds_to_win": 2
}
```

### 3.1.1 `room_joined` 里的 token

`room_joined` 会带上这个座位专属的 `token`（随机十六进制字符串），
客户端应把它保存在**每个标签页独立的会话存储（sessionStorage）**里，用于断线重连：

```json
{ "type": "room_joined", "room_code": "QXHX", "seat": 0, "token": "9f2c1a…", "score": [0, 0], "players": [] }
```

> ⚠️ 不要用 localStorage：同源的所有标签页共享它。双开测试时后加入的标签页会覆盖前一个的
> token，刷新后会把自己重连成对手的座位（这是实测踩到的坑）。

### 3.1.2 `state_sync`（重连后的一次性同步）

断线重连成功后，服务端立刻推送 `state_sync`：字段与 `round_start` 基本一致，
另外包含 `submitted`（自己是否已提交）、`plan`（自己已提交的方案）、
`opponent_ready`（对手是否已提交）与 `remaining_seconds`（备战剩余秒数），
客户端据此把界面恢复到断线前的样子。

掉线后房间会保留 **90 秒**（可由 `NC_RECONNECT_GRACE` 调整）等待重连；
超时未回来才关闭房间，并通知对手 `room_closed`。主动点「退出房间」则不保留，立即关房。

### 3.2 `battle_report`

```json
{
  "type": "battle_report",
  "round_index": 1,
  "score": [0, 0],
  "auto_submitted": [1],
  "plans": [{ "selection": [4, 10, 12], "bonuses": [], "strategy": {} }],
  "lineups": [[{ "uid": "A1-4", "name": "自爆步兵", "position": "A1", "hp": 3, "max_hp": 3, "tags": ["explosive"] }]],
  "result": {
    "winner_team": 0,
    "reason": "一方全灭",
    "rounds": 5,
    "seed": 123456,
    "first_team": 0,
    "total_initiative": [10, 14],
    "survivors": [2, 0],
    "event_count": 64,
    "events": [
      { "seq": 1, "round": 0, "kind": "battle_start", "text": "开战：第 A 队先手……", "data": { "teams": [] } },
      { "seq": 6, "round": 1, "kind": "damage", "text": "B2 均衡战士A 受到 8 点伤害，剩余 15/23",
        "data": { "target": "B2-1", "attacker": "A1-10", "amount": 8, "hp_after": 15, "lethal": false, "follow_up": false } }
    ]
  }
}
```

事件 `kind` 取值与用途：

| `kind` | 用途 |
| --- | --- |
| `battle_start` | 开战、先手判定、双方开战阵容快照 |
| `round_start` | 回合分隔（前端用它分段显示） |
| `curse` | 标签剥夺 |
| `attack` | 一次攻击宣告（含群伤覆盖的目标列表） |
| `damage` / `poison_tick` | 扣血（含 `hp_after`，前端据此更新血条） |
| `shield` / `tag` / `pierce` | 标签结算细节 |
| `poison` | 中毒叠加 |
| `heal` / `revive` | 恢复与复活 |
| `death` / `clash` | 阵亡与同归于尽 |
| `skip` | 已阵亡角色无法行动 |
| `battle_end` | 战斗结束与原因 |

### 3.3 私有信息边界

- 角色的**角色池**只通过 `round_start` 发给本人；
- 双方方案直到 `battle_report` 才会同时公开（此时战斗已经开始）；
- 对手只收到 `opponent_ready` 这类状态提示，不包含任何选角/增益内容。

### 3.4 模式隔离（重要）

一个房间的模式在创建时就定下来，之后**不会改变**。为了不让模式"串味"，协议层做了这些保证：

| 场景 | 行为 |
| --- | --- |
| 用房间号加入 | 以**房间的模式**为准；加入请求里即使带了 `mode` 字段也会被忽略 |
| 随机匹配 | 只在**相同模式**的队列里配对；不同模式的玩家永远配不到一起 |
| 队列里换模式 | 换模式会先退出旧队列，不会同时占两个队列 |
| 再来一局 | 沿用房间原模式（`rematch` 不接受模式参数） |
| 断线重连 | `state_sync` 会带上房间模式，客户端按房间恢复界面 |
| 客户端偏好 | 大厅选择的模式只影响"创建房间 / 随机匹配"，不会被加入的房间覆盖（前端分别保存 `lobbyMode` 与 `roomMode`） |

对应回归测试：`test_joining_by_room_code_adopts_the_room_mode`、`test_matchmaking_is_isolated_by_mode`、
`test_switching_matchmaking_mode_removes_the_old_queue_entry`、`test_rematch_keeps_the_room_mode`。

## 4. HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 前端单页应用 |
| GET | `/static/*` | 前端静态资源 |
| GET | `/api/health` | 健康检查：`{"status":"ok","version":"0.1.0","rooms":0,"players":0,"uptime_seconds":12.3}` |
| GET | `/api/version` | 名称、版本、协议版本、模式、规则版本 |
| GET | `/api/rules` | 规则页数据：常量、角色表、标签表、可选策略 |

`/api/rules` 是「让前端规则页永远与后端数值一致」的唯一数据源，改数值后无需改前端。

## 5. 错误处理约定

- 客户端消息不合法（JSON 格式、类型未知、必需字段缺失）→ `error`，`field` 指向具体字段，前端高亮提示；
- 规则不通过（选角数量、增益次数、自爆位置等）→ `error`，`message` 是可读中文，例如
  「需要选择 3 名角色出战，当前选择了 2 名」，`field` 为 `selection` / `bonuses` / `strategy`；
- 房间层面的失败（房间不存在、已满、阶段不对）→ `error`，`fatal=true` 表示需要重新建房；
- 服务端内部异常 → `error`，同时写日志，连接保持可用。
