# 开发流程与版本管理

这份文档存在的唯一目的：**让项目永远能回到一个可运行的稳定版本**。
之前的两次尝试之所以走不下去，是因为改动太大、提交太粗，出了问题没有干净的落点。

---

## 1. 分支模型

```text
main                    始终可运行，随时可以部署
 ├─ feat/<主题>          新功能：例如 feat/chaos-mode
 ├─ fix/<主题>           修 bug：例如 fix/room-cleanup
 └─ release/<版本>       发版前的收尾（可选）
```

> 早期还有一个 `legacy/novaclash2` 分支用来对照被放弃的旧实现，
> 已于 2026-09-25 删除（内容与本仓库历史无关，且会让人误以为要维护两份代码）。

| 规则 | 说明 |
| --- | --- |
| `main` 只接受通过测试的合并 | 合并前必须 `pytest` + `ruff` 全绿 |
| 一个分支只做一件事 | 主题变了就开新分支，别在同一个分支里塞两个功能 |
| 分支存活时间尽量短 | 长时间分支必然产生难解的冲突 |
| 合并方式 | 优先 `--no-ff` 合并保留分支轨迹，或直接快进合并 |

常用命令：

```bash
git switch -c feat/chaos-mode        # 开分支
git add -A && git commit -m "feat(rules): 支持随机标签角色池"
git switch main && git merge --no-ff feat/chaos-mode
git branch -d feat/chaos-mode
```

## 2. 提交规范

格式：`类型(范围): 说明`，说明写清「做了什么、为什么」，一次提交只做一件事。

| 类型 | 用途 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 文档 |
| `test` | 测试 |
| `refactor` | 不改变行为的重构 |
| `perf` | 性能 |
| `chore` | 依赖、配置、构建 |

范围建议：`engine` / `rules` / `room` / `web` / `ui` / `tools` / `docs` / `deps`。

```text
feat(engine): 新增斩杀标签的伤害修正
fix(web): 对手掉线后房间没有立即回收
docs(rules): 记录复活次数取 2 的原因
test(engine): 覆盖自爆对撞的同归于尽分支
```

**什么时候必须提交**：

- 写完一个可运行的小步骤（哪怕只是一个标签效果）；
- 修好一个 bug，并且补上了对应的测试；
- 调整了平衡数值（同时更新 `docs/规则设定.md` 与 `CHANGELOG.md`）。

**什么时候不要提交**：测试没跑通、功能做了一半无法运行、把无关改动混在一起。

## 3. 版本号怎么算、tag 怎么打

### 3.1 一句话规则

> **只有"玩家能感知的新玩法 / 新能力"才 +0.1；修 bug 才 +0.0.1；
> 文档、重构、测试、素材、部署 → 不进版本号，跟着下一个版本发。**

版本号只写在 `backend/__init__.py`（`__version__`），**只有发版时才动它**。
平时部署一百次也不用改版本号——部署点和版本号是两件事。

### 3.2 判定表

| 改动 | 版本号 | 例子 |
| --- | --- | --- |
| 新玩法 / 新能力，玩家能直接感觉到 | **+0.1** | 补卡、练习模式、卡牌拖放、三种模式 |
| 现有功能的修复（线上已经出问题） | **+0.0.1** | 匹配把自己配给自己、结算页丢失 |
| 重新设计既有交互（体验明显不同） | **+0.1**（并写进 CHANGELOG 的"交互"小节） | 按钮模式 → 卡牌模式 |
| 文档 / 重构 / 补测试 / 美术素材 / 部署脚本 | **不动** | 介绍页与规则页（内容页）、零构建拆分、CI 调整 |
| 平衡数值微调 | **不动**，并入下一个版本 | 某张卡 +1 攻 |

> 拿不准时问自己一句：**"玩家会不会注意到？"** 会 → 才值一个号码。

### 3.3 部署点用部署 tag，不占用版本号

想留"能一键回去的点"时，打一个按日期编号的轻量 tag 就够了：

```bash
# 日常部署：只是留一个回退点，不抬版本号
git tag deploy-2026-09-19.3 -m "线上部署点：练习模式上线前的补丁"
git push origin deploy-2026-09-19.3

# 真正的发版：更新 backend/__init__.py 的版本号 + CHANGELOG，再打版本 tag
git tag -a v0.13.0 -m "v0.13.0：<一句话说清玩家得到了什么>"
git push origin main --tags
git tag -l                        # 查看所有可回退的点
```

回滚时用哪个都行（`git checkout <tag> && bash deploy/update.sh`），
区别只是：**版本 tag 是对外承诺，部署 tag 是内部书签。**

### 3.4 复盘：为什么 0.8 ~ 0.12 走得太快

上线当天把 `v0.8.0 → v0.12.0`（含 0.11.1 / 0.11.2）连着打了出来，一天十个 tag。
内容都是真的，但**节奏不对**：其中"介绍页/规则页"属于内容页（按上表不该占版本号），
两个匹配 bug 应该并成一个 +0.0.1，`0.11.x` 这种中间号完全没必要出现。
按现在的规则重排，那天应该是：

| 那一天实际发生了什么 | 现在会怎么发 |
| --- | --- |
| 卡牌模式 + 战斗演出 + 音效 | `v0.8.0` |
| 角色池固定 + 回放不计时 + 备限 90 秒 + 赛后结算页 | `v0.9.0` |
| 补卡 + 整场平衡对拍 | `v0.10.0` |
| 介绍页 / 规则页 | 不占版本号，跟下一版一起发 |
| 两个匹配 bug 的修复 | 合并成一次 `v0.10.1`（部署 tag 另留） |
| 练习模式 + 显示对手 + 队列加固 | `v0.11.0` |

历史 tag 保持不动（它们是有效的回退点，删掉反而损失可回退性），
从下一个版本开始按上面的节奏走。

### 3.5 下一个大号留给 1.0

`1.0.0` 不用等新玩法，等到**这几件事同时成立**就发：

1. 核心闭环（建房/匹配 → 备战 → 演算 → 结算 → 再来一局）连续一周线上无阻塞性 bug；
2. 有外部玩家真的在玩（不是只有我们自己测）；
3. 规则 / 协议 / 部署 / 回滚四份文档与实现一致；
4. 有一套"出问题能自己发现"的可观测手段（`/api/health` 那类）。

在那之前，版本号停在 `0.x` 完全够用，不必为了"看起来在推进"而抬号。

## 4. 发布检查清单

发版（打 tag）前逐项打勾：

- [ ] `./venv/bin/python -m pytest -q` 全绿；
- [ ] `./venv/bin/ruff check .` 无告警；
- [ ] 改了前端 JS 时逐个 `node --check frontend/js/*.js` 通过；
- [ ] 版本号确实该抬（见第 3 节的判定表），而不是"顺手加一"；
- [ ] 用 `tools/smoke_pvp.py` 在真实服务上跑完一整套三局两胜；
- [ ] 手动点一遍：创建房间 → 加入 → 备战 → 提交 → 战斗回放 → 结算 → 再来一局；
- [ ] 更新 `CHANGELOG.md` 与 `docs/规则设定.md`（若有数值变化）；
- [ ] 更新 `docs/开发路线图.md` 的完成状态；
- [ ] `git status` 干净，没有忘记加的文件；
- [ ] 打 tag 并推送：`git push origin main --tags`。

## 5. 回滚剧本

### 5.1 线上出问题，但想保留历史

```bash
git log --oneline -10              # 找到出问题的提交
git revert <commit>                # 生成一条反向提交
git push origin main
```

`revert` 会留下记录，团队能看到「什么被撤回了」，推荐优先使用。

### 5.2 本地改乱了，想回到稳定版本

```bash
git switch main
git fetch --tags
git checkout v0.1.0                # 直接回到稳定版本（只读观察）
git switch -c fix/rollback         # 想在此基础上继续改就开分支
```

### 5.3 只想撤销工作区里没提交的改动

```bash
git status                         # 先看清楚动了哪些文件
git restore <文件>                  # 丢弃指定文件的改动
git restore --staged <文件>          # 撤销暂存
```

> 危险操作（`git reset --hard`、`git checkout -- <文件>`）会直接丢数据，
> 只有在确认没有未提交成果时才使用。

### 5.4 想找回几天前删掉的代码

```bash
git log --oneline --all -- <路径>          # 找到涉及该文件的提交
git show <commit>:<路径>                   # 查看当时的完整内容
git checkout <commit> -- <路径>            # 把文件恢复到工作区
```

### 5.5 想对照被放弃的旧实现

被放弃的旧实现（`client/` + `server/`，2026-07）已不在本仓库里，
需要对照时用本地归档的 bundle：

```bash
git clone .ops/archive/novaclash2-legacy.bundle /tmp/novaclash2-legacy
git show legacy/novaclash2:server/game/engine.py | less   # 在 /tmp/novaclash2-legacy 里执行
```

> 注意：旧实现本身有问题（数值与文档不一致、结构耦合），只作为对照，不要直接回退。

## 7. 日常开发流程示例

### 7.1 调整平衡数值

```bash
git switch -c feat/balance-v0.2
# 1. 只改 backend/core/constants.py
# 2. ./venv/bin/python -m tools.cli --auto 200   # 看胜率是否健康
# 3. 更新 docs/规则设定.md 的数值表与 CHANGELOG.md
# 4. pytest + ruff
git commit -m "feat(balance): 狂战士狂暴倍率 1.4 → 1.5，并记录对拍结果"
```

### 7.2 新增标签

```bash
git switch -c feat/tag-lifesteal
# 1. tags.py 注册 TagSpec 与 TagRuntime（吸血 = on_hit 钩子）
# 2. characters.py 里挂到噬魂者身上
# 3. tests/test_engine.py 补边界用例（回复上限、自爆不触发）
# 4. docs/规则设定.md 补标签说明与结算顺序
git commit -m "feat(engine): 新增吸血标签（25% 回复，单次上限 5）"
```

### 7.3 修 bug

```bash
git switch -c fix/room-cleanup
# 1. 先写一条会失败的测试，确认它确实复现了问题
# 2. 改实现让测试通过
git commit -m "fix(web): 修复房间长时间无活动未被回收的问题"
```

## 8. 不进入版本库的内容

`.gitignore` 已经覆盖：虚拟环境（`venv/`）、`__pycache__`、本地配置（`.env`）、
编辑器与系统文件（`.DS_Store` / `.idea` / `.vscode`）、运行产物（`logs/`、`data/`、`*.log`）。

需要新增忽略项时，优先在 `.gitignore` 里加规则，而不是把文件手动移出目录。
