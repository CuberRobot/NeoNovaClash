# 项目历史与旧资料去向

这份文档解释「这个项目从哪来、旧的东西去哪了」，避免以后翻不到出处，
也避免把历史包袱留在工作区里越堆越乱。

## 时间线

| 时间 | 阶段 | 结果 |
| --- | --- | --- |
| 2026-01 ~ 02 | **手写规则碎片**：在 `Code/CL1`、`NCinit` 里手写对战循环、角色表与标签判定，边写边想 | 规则雏形成型（12 角色 / 9 标签 / 6 选 3 / 4 次增益），但代码是「脚本式」的，难以扩展 |
| 2026-02 ~ 04 | **第一次重构 NovaClash**：把玩法抽出来做成前后端，补了 20 角色、12 标签、混沌模式、大战场 | 玩法文档非常完整，但实现逐渐失控，最终无法回退 |
| 2026-07 | **第二次重构 NovaClash2**：改用 FastAPI + WebSocket 重写 | 结构好了一些，但仍是「带着旧逻辑重写」，数值与文档对不上，再次走入死胡同 |

| 2026-09 | **交互大版本与规则修正**：卡牌模式 + 战斗演出（v0.8.0），角色池整场固定 / 90 秒备限 / 回放不计时 / 结算页可恢复（v0.9.0） | 从"看数据"变成"看打斗"，并把"猜对手"真正做成玩法核心——这些都来自真人试玩后提出的问题 |

| 资料 | 位置 | 说明 |

| 玩法与设定文档 | 已整理进 [规则设定.md](规则设定.md)「数值裁定」一节 | 冲突的地方都记录了取舍理由 |

## 为什么要把碎片移出工作区

1. 它们和正式代码是**两套完全不同的写法**（脚本式、全局变量、交互式 `input()`），留在仓库里容易被误引用；
2. 静态检查、测试与打包都没必要覆盖这些历史文件；
3. 出处与思路已经完整记录在本文档与规则设定里，代码本身不再需要放在眼前。

## 从这段历史里保留下来的三条做法

1. **小步提交 + 里程碑打 tag**：每完成一块能跑的东西就提交，能跑通的版本一定打 tag；
2. **数值与文档同源**：平衡数值只写在 `backend/core/constants.py`，规则文档与游戏内规则页都从这里派生；
3. **先写测试再调数值**：任何平衡调整都先跑 [../tools/balance.py](../tools/balance.py) 拿到数据，改完再跑一遍验证。
