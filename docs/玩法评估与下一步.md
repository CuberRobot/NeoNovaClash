# 玩法评估：上限卡在哪、接下来怎么走

> 立项日期：2026-09-25（同日完成运维改造之后）
> 这份文档回答：**当前玩法的天花板是什么、哪些是机制问题哪些是产品问题、下一步有哪几条路**。
> 现状数据见 [下一阶段规划 §1](下一阶段规划.md)，历史版本见 [开发路线图](开发路线图.md)。

---

## 1. 结论先说

**"这个游戏上限低"是准确的判断，但原因不是数值不平衡或内容不够，而是结构性的：
它是一个"开打前一次性决策、之后零操作"的游戏。**

它借用了德州扑克的形状（有限信息 + 隐藏意图 + 一次性亮牌），却**没有下注轮**：
扑克的深度来自"信息逐步公开 + 每一轮重新决策"，而这里所有决定都在开打前提交完毕，
之后玩家只能看动画。所以它现在既没有即时操作，也没有 meta 深度。

---

## 2. 用代码里的真实结构量化

### 2.1 单局决策空间（v0.12.0，标准模式）

| 决策 | 规模 | 计算 |
| --- | --- | --- |
| 6 选 3，**选择顺序即出击顺序** | 120 | `C(6,3) × 3!` = 20 × 6 |
| 4 次增益分配（攻击+2 / 生命+4，单格 ≤2 次） | **6** | 分布只有 `(2,2,0)` 与 `(2,1,1)` 两类，各 3 种排列 |
| 攻击策略（血最低 / 攻最高 / 指定标签） | 15 | 2 个无参 + 12 种有效标签（`tags.TAGS` 去掉 `none`） |
| **合计** | **≈ 10,800** | 120 × 6 × 15 |

一万量级的决策空间对一个策略游戏本来不算小——**问题在于这个空间只被探索一次，
而且必须在 90 秒内交卷，之后不可修改。**

### 2.2 为什么"猜对手"撑不起深度

设计意图是"整场三局共用一份固定角色池，核心是猜对手会怎么用他手上那 6 张牌"（见 [规则设定](规则设定.md) §1）。
这个博弈成立的前提是**双方都懂 meta**：

- 你得知道"6 张里哪 3 张是强势组合、对手大概率怎么排"；
- 对手也得知道，这样你们才在同一层博弈。

而真实数据是：**上线 7 天、20 个 IP、7 场战斗**（[下一阶段规划 §1.1](下一阶段规划.md)）。
没有任何玩家可能形成 meta，所以现在这个博弈**在玩家感受到之前就已经失效了**——
你面对的其实是一个随机对手，随机对手没有"意图"可猜。

### 2.3 战斗过程没有决策点（这是结构性事实）

- 出招顺序固定 `A1→B1→A2→B2→A3→B3`，先手由先手值总和高低决定，**没有可干预的机制**；
- 目标选择由策略机械决定（`engine.py` 的 `Battle.choose_target`），
  玩家能表达的全部意图就是三个策略之一；
- 战斗完全确定性（整数运算 + 固定种子），同一份输入永远同一份战报——
  这对复盘、测试、平衡对拍是优点，但**代价是"看战报"和"看结果"没有区别**；
- 战斗中唯一的交互是回放控制（暂停/加速/跳结果）。

### 2.4 三种模式是同一件事换参数

`backend/core/modes.py` 的 `ModeConfig` 只改：池子大小（6/6/9）、出战人数（3/3/5）、
增益次数（4/4/6）、是否随机标签、标签数上限。

**没有任何一个模式新增决策维度或改变信息结构。** 所以再出第 4 个模式也不会有质变——
这也是《下一阶段规划》把"新增第 4 个模式"列入"不做"的正确理由。

### 2.5 投入产出不匹配

| 指标 | 现状 |
| --- | --- |
| 一局时长 | 2~4 分钟（含整段战斗演出） |
| 三局两胜 | 6~12 分钟 |
| 其中真正的决策时间 | 约 30~60 秒（其余是看演出、等对手、看对手看演出） |

## 3. 必须分清：这是两个不同的问题

| | 问题 A：产品/留存 | 问题 B：玩法深度 |
| --- | --- | --- |
| 表现 | 点进来的人没打完第一局就走 | 会玩的人觉得"一眼看到底" |
| 证据 | 20 IP / 7 场战斗 | 决策空间一次性、战斗零干预 |
| 修法 | 新手路径、分享、电脑对手升级 | 改变信息结构或增加决策轮次 |
| 成本 | 低（十几小时） | 中~高（协议 + 前端 + 平衡重做） |
| 天花板 | **提不了玩法上限**，只提完成率 | 才是真正抬上限 |

**别把 A 当成 B 来修**：新手路径做完，第一局完成率会涨，
但"这游戏上限低"这个判断不会变。反之，直接做 B 而不修 A，
会变成"更好玩但依然没人玩到"。

**明确不是问题的部分**（免得改错地方）：

- 引擎质量是资产，不是负债：可复现种子、事件化战报（可分享/统计/二次利用）、
  模式配置化、`tools/balance.py` 对拍工具。**瓶颈在决策层，不在模拟层。**
- 数值平衡已经达标（20 名角色 45%~55%），现在没有真人样本，**继续调数值是浪费**。

## 4. 三条路

### 路线 1：只修产品（不改机制）

做《下一阶段规划》§3.2 那 5 项：首屏"先跟电脑打一局"、备战一次性引导、
结算页"换模式再打"、分享本局战报、战绩本地化。

- **成本**：低，一两周。
- **收益**：把"来了就走"变成"至少打完一局"，这是所有后续验证的前提。
- **代价**：玩法上限不变。你（作者）大概还是不会想玩第二遍。
- **适用**：定位是"给朋友交差"或"先验证有没有人愿意玩"。

### 路线 2：给机制补上"第二轮决策"（推荐的主线）

核心动作：**把一次提交拆成"先亮意图、再定细节"两段**，让信息在中途公开。

具体设计（待细化，作为 v0.13/v0.14 的候选）：

1. **第一段**：只提交"出战顺序"（选哪 3 名 + 排位）。对手看到你的阵容与顺序；
2. **第二段**：看到对手阵容后，再提交"4 次增益 + 攻击策略"。这一段的决策带着新信息，
   才真正是"读对手"；
3. 结果：单局决策次数 1 → 2，且第二次是在信息更新后做的。

- **成本**：中。协议加阶段字段（`submit_plan` 拆两段）、房间状态机加一个子阶段、
  前端备战页加一步、计时器拆分（例如 60s + 60s）。
- **收益**：复用现有引擎与全部素材，**把扑克缺的那一轮下注补回来**，
  且不改变"三局两胜 + 固定池"的骨架。
- **风险**：一局从 90 秒变 150~180 秒，需要实测会不会更劝退。

> 备选子方案：只把"排位"改成**同时亮牌**（双方先各交顺序、互相可见后再各自交增益/策略），
> 信息揭示更彻底，但两端实现复杂度更高。建议先做上面的两段式。

### 路线 3：换成另一种游戏形状（保留引擎与素材）

引擎本质是"两队列自动对撞 + 事件流"，适合的形状不止现在这一种：

| 形状 | 与现有代码的复用度 | 说明 |
| --- | --- | --- |
| 自走棋式布阵（按轮次买/放/合成，自动对撞） | 高 | 复用战斗引擎与事件流，决策密度高得多 |
| Roguelike 卡牌构筑（对 AI 的 PvE 连战） | 中 | 复用战报与标签系统，需要新的成长/构筑层 |
| 单机解谜（给定池子与对手，找出最优解） | 中 | 复用引擎的确定性，正好利用"可复现"这个优点 |

- **成本**：高（等于做新游戏，只是省了战斗引擎）。
- **收益**：如果目标是"做一个真有人玩的东西"，这可能是唯一能真正抬上限的路。
- **适用**：定位是长期项目、且愿意推倒重来。

## 5. 不做清单（防止再次膨胀）

| 不做 | 原因 |
| --- | --- |
| 新增第 4 个模式 | 模式只是换参数，不解决决策层问题 |
| 在没有真人样本时继续调数值 | 7 场战斗连一个角色胜率都算不出来 |
| 在没有定位共识前做路线 3 | 成本最高，方向错了浪费最大 |
| 给当前玩法加更多演出/音效/特效 | 演示不是瓶颈；演出越长，投入产出比越差 |

## 6. 需要拍板的两件事

| # | 问题 | 选项 |
| --- | --- | --- |
| 1 | **这个项目的定位是什么？** | ①给朋友交差 ②自己的长期项目 ③验证"能不能有人玩" |
| 2 | 定位决定路线 | ①→只做路线 1 然后收工；②→做路线 1 + 路线 2；③→先做路线 1，用日志看一周数据再定 |

> 定位 ③ 现在**终于可测了**：运维改造后（[运维手册](运维手册.md)），
> `grep -c room_created` = 开局数、`grep -c match_over` = 完成数，
> 两个一比就是完成率。这是这一轮运维工作最大的直接收益。

## 7. 工程侧顺带发现（与玩法无关，留作欠账）

| 发现 | 影响 | 建议 |
| --- | --- | --- |
| `active_players()` 把练习模式的**电脑对手**也算作在线玩家 | `/api/health` 的 `players` 会虚高，且 `room_list` 里练习房间与真人对局混在一起 | 分开统计（`players` 只算真人，另给 `bot_rooms`） |
