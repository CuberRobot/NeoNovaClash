# NeoNovaClash · 星陨竞技场

双人战前部署、自动演算的回合制策略对战。
两名玩家各自拿到 6 名随机星灵，选出 3 名、排定出击顺序、分配 4 次增益、设定攻击策略；
双方提交后由服务端一次性演算出整场战斗的回放，三局两胜决出胜负。

> **当前版本：v0.4.0（标准模式）**
> 内容范围：20 名角色（12 基础 + 8 扩展）、12 种标签、6 选 3、4 次增益、三局两胜。
> 已完成一轮平衡调整（8000 场对拍，全部角色落在 45%~55% 胜率区间）与抽池机制优化。
> 已经跑通的完整链路：`建房 → 对手加入 → 备战（选人/增益/策略）→ 自动战斗回放 → 本局结算 → 下一局 → 整场结算 → 再来一局`。

**在线 demo**：<http://189.24.77.139/>（部署在宝塔面板的 Debian 服务器上，做法见 [docs/宝塔面板部署.md](docs/宝塔面板部署.md)）

## 1. 快速开始

```bash
git clone <本仓库地址> && cd NeoNovaClash

python3 -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt

python run.py                     # 默认监听 http://127.0.0.1:8000
```

打开两个浏览器标签页（或两台设备）访问同一个地址：

1. 第一个标签页填写昵称 → **创建房间**，拿到 4 位房间号；
2. 第二个标签页填写昵称 → 输入房间号 → **加入房间**；
3. 两人到齐后自动进入第一局备战：点角色卡选出 3 名（点击顺序 = 出击顺序）、
   用 **+攻击 / +生命** 分配 4 次增益、选择攻击策略，然后提交；
4. 双方提交（或 60 秒超时）后自动开战，战报逐条播放，血条实时变化；
5. 先赢 2 局的一方拿下整场，房间内可以直接「再来一局」。

> 只想验证规则、不打开浏览器？见 [命令行对战](#4-常用命令) 一节。

## 2. 玩法一页看懂

| 环节 | 规则 |
| --- | --- |
| 角色池 | 从 20 张共用抽 12 张后对半切：双方不重复，且两边池子强度接近（每池至少 2 个带标签角色） |
| 选角 | 选出 3 名，**选择顺序即出击顺序** |
| 增益 | 共 4 次：攻击 +2 / 生命 +4，单个出击位最多 2 次 |
| 策略 | 优先打血量最低 / 攻击最高 / 指定标签 |
| 先手 | 双方出战角色先手值总和较低者先手，相同则随机 |
| 出手 | 按 A1 → B1 → A2 → B2 → A3 → B3 依次行动，先手方在同一位次先动 |
| 结束 | 一方全灭立即结束；单局最多 50 回合，超时按剩余总血量判定 |
| 胜负 | 三局两胜；双方同归于尽则该局重开（比分不变） |

完整规则、数值与裁定说明见 **[docs/规则设定.md](docs/规则设定.md)**。

## 3. 项目结构

```text
backend/                 服务端
  config.py              运行配置（全部来自环境变量）
  protocol.py            前后端消息协议：下行消息构造 + 入站消息校验
  web/                   Web 层（FastAPI）
    app.py               HTTP 路由、WebSocket 挂载、静态资源
    hub.py               房间注册表、连接管理、后台推进与回收
    websocket.py         连接生命周期与指令分发
  core/                  纯游戏逻辑（不依赖任何 Web 框架）
    characters.py        角色数据
    constants.py         平衡数值（唯一来源）
    tags.py              标签定义与效果钩子
    models.py            运行时模型：方案、战士、事件、战斗结果
    engine.py            战斗引擎（可复现、可回放）
    rules.py             角色池、方案校验、阵容构建
    room.py              房间与对局状态机
frontend/                原生 HTML/CSS/JS 单页应用（无构建步骤）
deploy/                  部署模板：systemd 服务、nginx 反代、一键更新脚本
tools/                   开发工具：命令行对战、联机冒烟测试
tests/                   引擎 / 规则 / 接口 / 联机流程测试
docs/                    规则、架构、协议、部署、版本管理、路线图
legacy/                  旧手写碎片归档（仅作参考，不参与构建）
```

分层原则：**core 不依赖 web，web 不写游戏规则**。
战斗引擎拿到「两份阵容 + 策略 + 随机种子」就能算出同一份战报，
因此规则可以被测试、对拍与复现，而不需要启动服务器。

## 4. 常用命令

```bash
# 跑全部测试（引擎标签效果、规则校验、HTTP、WebSocket 全流程）
./venv/bin/python -m pytest -q

# 代码检查
./venv/bin/ruff check .

# 命令行热座对战：两名玩家轮流输入，直接看战报
./venv/bin/python -m tools.cli

# 随机方案自动对拍 N 场，用于平衡性抽样
./venv/bin/python -m tools.cli --auto 200

# 联机冒烟测试：两个机器人客户端在真实服务上跑完整场三局两胜
./venv/bin/python run.py                     # 先启动服务
./venv/bin/python -m tools.smoke_pvp --verbose

# 平衡对拍：角色抽到率 / 出战率 / 出战胜率（调数值前先跑它）
./venv/bin/python -m tools.balance --battles 8000

# 接口自检
curl http://127.0.0.1:8000/api/health
curl http://127.0.0.1:8000/api/rules | head
```

## 5. 配置项

复制 `.env.example` 为 `.env` 后修改，或直接注入环境变量（容器部署推荐后者）。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `NC_HOST` | `0.0.0.0` | 监听地址 |
| `NC_PORT` | `8000` | 监听端口 |
| `NC_PREPARE_TIMEOUT` | `60` | 备战限时（秒），超时自动随机提交 |
| `NC_ROOM_TTL` | `1800` | 等待中/已结束房间的空闲回收时间（秒） |
| `NC_MAX_ROOMS` | `500` | 单进程最大房间数 |
| `NC_LOG_LEVEL` | `info` | uvicorn 日志级别 |

## 6. 部署

三种方式，任选其一，详见 **[docs/部署指南.md](docs/部署指南.md)**：

```bash
# A. 直接跑 uvicorn（最简单）
./venv/bin/uvicorn backend.web.app:app --host 0.0.0.0 --port 8000

# B. Docker
docker compose up --build -d

# C. 反向代理（nginx + WebSocket 升级头）
#    参考 docs/部署指南.md 中的 nginx 片段

# D. 宝塔面板 / 云服务器（systemd + nginx）
#    仓库自带模板：deploy/neonovaclash.service、deploy/nginx.neonovaclash.conf、deploy/update.sh
#    完整步骤见 docs/宝塔面板部署.md
```

服务是无状态的（房间只存在内存里），因此**水平扩容时必须开启会话粘滞（sticky session）**，
或者把房间状态迁移到 Redis —— 这一项已列入 [路线图](docs/开发路线图.md)。

健康检查：`GET /api/health` 返回 `{"status": "ok", ...}`。

## 7. 版本管理与回滚

这个仓库刻意把「怎么回退」写进文档，避免再出现无法回滚的情况：

- `main` 分支永远保持可运行；每个里程碑打 tag（当前 `v0.4.0`）；
- 功能开发走 `feat/xxx` 分支，合并前必须 `pytest` + `ruff` 全绿；
- 每次提交只做一件事，提交信息写清「改了什么、为什么」；
- 回滚优先用 `git revert <commit>`（保留历史），紧急时 `git checkout v0.1.0` 回到上一个稳定版本。

完整分支模型、提交规范与回滚剧本见 **[docs/开发流程与版本管理.md](docs/开发流程与版本管理.md)**。

## 9. 设计原则

1. **规则与传输分离**：战斗引擎只吃数据结构，WebSocket 只做搬运，任何一方都能单独测试。
2. **数值只有一个来源**：所有平衡数字集中在 `backend/core/constants.py`，角色数据集中在 `characters.py`。
3. **可复现**：每局战斗都有种子，相同输入必然得到同一份战报，方便复盘与平衡分析。
4. **为用户着想**：提交前实时告诉玩家「还差什么」，超时会自动提交，断线/对手离开都有明确提示与出口。
5. **小步提交**：功能一次只加一层，配套测试与文档一起提交，任何时候都能回到上一个可用版本。
